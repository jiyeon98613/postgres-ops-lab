# 01. 정기 백업 복구와 테이블 삭제 복구

## 목적

운영 중인 문서 수집·청구 시스템의 정기 백업을 실제로 복원할 수 있는지 확인했습니다. 복원 명령의 종료 상태와 함께 테이블 누락, 데이터 값, 인덱스와 제약조건을 점검했습니다. 실수로 테이블을 삭제한 상황도 별도 DB에서 재현했습니다.

## 실행한 명령

[공통 환경 설정](../../README.md#실행-환경과-순서) 후, 완료된 custom-format 백업 파일을 지정했습니다. 기존 정기 백업을 사용했으며 이번 실습에서 백업 스케줄을 새로 설정하지는 않았습니다.

```bash
python scripts/restore.py \
  --dump "$BACKUP_FILE" \
  --workspace "$LAB_WORKSPACE" \
  --pg-bin /usr/lib/postgresql/18/bin

python scripts/drop_restore.py \
  --workspace "$LAB_WORKSPACE" \
  --pg-bin /usr/lib/postgresql/18/bin
```

[복구 스크립트](../../scripts/restore.py)는 백업을 비공개 작업 디렉터리에 복사하고, `pg_restore --no-owner --no-acl --single-transaction --exit-on-error`로 빈 DB에 복원했습니다. 복사 전후 원본 파일의 크기와 수정 시각을 비교해 복사 중 백업 파일이 바뀌지 않았는지도 확인했습니다.

백업의 COPY 데이터와 복원 DB의 COPY 데이터를 같은 출력 형식으로 읽어 테이블별로 비교했습니다. 각 행의 SHA-256을 정렬해 비교하므로 행 순서가 달라도 값과 중복 개수가 같으면 일치로 처리했습니다. 백업 목차의 테이블 수와 검증한 테이블 수도 대조했습니다.

[삭제 복구 스크립트](../../scripts/drop_restore.py)는 별도 DB의 `staging.change_items`를 삭제한 뒤, 다른 빈 DB에 같은 백업을 전체 복원했습니다. 이후 삭제한 테이블과 나머지 테이블의 값까지 다시 비교했습니다.

## 결과

2026-10-17에 생성된 5,229,374바이트 백업을 PostgreSQL 18.6에 복원했습니다.

| 확인 항목 | 결과 |
| --- | --- |
| 복원한 테이블·행 | 62개·32,117행 |
| 백업과 복원 데이터 비교 | 전체 테이블의 값과 중복 개수 일치 |
| 유효하지 않은 인덱스 | 0개 |
| 미검증 제약조건 | 0개 |
| 삭제한 수집 이력 테이블 | 삭제 전·복구 후 모두 2,692행, 값 일치 |
| 삭제 후 전체 복구 검증 | 62개 테이블 모두 백업과 일치 |
| 최초 `pg_restore` 실행 시간 | 1.0961초 |
| 삭제 실험 후 `pg_restore` 실행 시간 | 0.9674초 |

62개에는 Alembic 버전 관리 테이블 1개가 포함됩니다. 백업의 `SEQUENCE SET` 항목은 0개여서 실제 백업에서 대조할 시퀀스는 없었습니다. 시퀀스 비교 코드의 동작은 별도의 일회용 데이터로 확인했습니다.

측정 시간은 `pg_restore` 명령 실행 시간입니다. 장애 감지, 서버 준비, 애플리케이션 재시작과 접속 전환은 포함하지 않았습니다.

결과 파일: [최초 복원](../../results/restore.json), [삭제 후 복구](../../results/drop-restore.json)

## 막혔던 점

이번 실제 백업의 복원 과정에서 별도의 실행 오류는 기록되지 않았습니다. 다만 복구 범위를 판단할 때 확인할 부분이 남았습니다. `--no-owner --no-acl`로 복원했기 때문에 운영 계정의 소유권과 권한까지 복구했다고 볼 수는 없었습니다. 외부 PDF·문서 파일과 PostgreSQL 서버 설정도 이번 검증에 포함하지 않았습니다.

또한 현재 비교 코드는 COPY 테이블과 시퀀스를 대상으로 합니다. Large Object나 materialized view 데이터가 있는 백업은 검증 항목을 추가하기 전까지 중단하도록 했습니다. 행 값 비교에 쓰는 날짜·시간·숫자 출력 형식이 다를 때도 비교 실패를 무시하지 않도록 했습니다.

## 배운 점

복구 완료 기준에 테이블 수와 행 수뿐 아니라 실제 값의 일치를 포함해야 한다는 점을 확인했습니다. 테이블 삭제 후에도 전체 백업과 대조해, 삭제한 테이블 외에 누락된 데이터가 없는지 확인할 수 있었습니다.

이번 논리 백업으로 돌아갈 수 있는 시점은 백업에 포함된 스냅샷까지입니다. 백업 파일의 수정 시각만으로 정확한 복구 시점을 단정할 수 없고, 그 이후 변경분을 복구하려면 물리 백업과 WAL이 필요했습니다. 이 부분은 [스트리밍 복제·PITR 실습](../04-replication-pitr/README.md)에서 이어서 검증했습니다.
