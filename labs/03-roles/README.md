# 03. 계정별 권한 분리

## 목적

읽기 전용 계정, 애플리케이션 계정, 스키마 소유자의 권한을 나누고, 각 계정으로 실제 로그인해 허용한 작업과 차단한 작업을 확인했습니다. 실습 DB에 필요한 권한만 부여하고, 이후 생성한 테이블에도 기본 권한 설정이 적용되는지 검증했습니다.

## 실행한 명령

[SQL 비교 실습](../02-query-tuning/README.md)의 `masked` 모드까지 실행한 뒤, 생성된 `query_check` DB를 사용했습니다.

```bash
python scripts/roles.py \
  --workspace "$LAB_WORKSPACE" \
  --pg-bin /usr/lib/postgresql/18/bin
```

[권한 검증 스크립트](../../scripts/roles.py)에서 `PUBLIC`의 DB 접속·관련 스키마 권한을 회수하고 계정별 권한을 부여했습니다. 세 계정 모두 슈퍼유저, DB 생성, 역할 생성, 복제 권한은 부여하지 않았습니다.

각 계정에 서로 다른 비밀번호를 설정하고 SCRAM 인증으로 접속했습니다. 이력 조회는 복제한 테이블에서, 쓰기와 DDL은 별도의 `role_probe` 스키마에서 검사했습니다. 각 SQL 검사 뒤에는 트랜잭션을 rollback했습니다.

스키마 소유자로 `ALTER DEFAULT PRIVILEGES`를 설정한 뒤 새 테이블을 만들고, 읽기 전용 계정이 조회할 수 있는지도 확인했습니다.

## 결과

| 계정 | 성공한 작업 | 거부된 작업 |
| --- | --- | --- |
| `lab_readonly` | 이력 조회, 이후 생성한 테이블 조회 | INSERT·UPDATE·DELETE·DROP |
| `lab_application` | 이력 조회, 테스트 테이블 INSERT·UPDATE | DELETE·CREATE TABLE·DROP·소유자 역할 전환 |
| `lab_owner` | 소유한 테스트 스키마의 CREATE TABLE·DELETE | 역할 생성 |

SQL 허용·거부 검사 16개와 잘못된 비밀번호의 인증 거부 검사 1개, 총 17개를 통과했습니다. SQL 권한 거부는 모두 `42501`로 확인했습니다. 스키마 소유자도 새 역할을 만들 수 없었습니다.

결과 파일: [계정별 검사 결과](../../results/roles.json)

## 막혔던 점

이번 실행에는 예상하지 못한 오류를 수정한 기록은 없습니다. 다만 SQL 실행 실패와 로그인 실패는 서로 다른 기준으로 판정했습니다. 권한 거부는 `42501`을 확인했고, 로그인 실패는 드라이버가 SQLSTATE를 제공하지 않을 수 있어 비밀번호 인증 실패 여부를 별도로 확인했습니다. 다른 이유로 실패한 SQL이 권한 차단 성공으로 집계되지 않도록 했습니다.

운영에 적용할 권한 범위도 이번 실습만으로 확정할 수는 없었습니다. 예를 들어 애플리케이션의 DELETE 권한은 실습에서 차단했지만, 실제 업무 기능에 필요한지는 운영 코드와 제한 함수의 계약을 함께 확인해야 합니다.

## 배운 점

권한 설정은 허용한 작업의 성공과 금지한 작업의 실패를 함께 확인해야 했습니다. 계정으로 직접 로그인하니 인증과 SQL 권한을 구분해서 검증할 수 있었습니다.

기존 테이블의 권한과 앞으로 생성될 테이블의 권한도 따로 확인했습니다. 스키마 소유자가 만든 새 테이블에 기본 권한이 적용되는 것까지 검사했습니다. 이번 결과는 실습 계정의 권한 검증이며, 운영의 환자별·업체별 접근 통제까지 검증한 결과는 아닙니다.
