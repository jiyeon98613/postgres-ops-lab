# 02. 실제 조회 SQL의 기존 인덱스 비교

## 목적

문서 수집 과정에서 이전 처리 이력을 찾는 SQL을 대상으로, 이미 사용 중인 복합 인덱스가 조회에 얼마나 도움이 되는지 확인했습니다. 운영 백업을 복원한 DB에서 해당 인덱스 하나의 유무만 바꿔 실행 시간과 실행계획을 비교했습니다.

대상은 애플리케이션의 `document_discovery._previous_items()`가 사용하는 조회입니다. 업체와 Drive 파일 ID로 `staging.change_items`를 좁히고, `staging.change_sets`와 결합해 최신 이력부터 가져옵니다. 조회 조건과 연결되는 기존 인덱스를 비교 대상으로 선정했습니다.

```sql
CREATE INDEX ix_change_items_vendor_business_created
ON staging.change_items (vendor_id, business_key, created_at);
```

이 인덱스는 기존 migration `a8d4f2c61b90`에 정의되어 있었습니다. 배포된 조회 함수와 기준 코드가 일치하고, 실제 백업에도 인덱스가 존재하는지 확인했습니다. [대상 SQL](../../sql/discovery-history.sql), [소스·인덱스 확인 결과](../../results/source-context.json)

## 실행한 명령

[백업 복구 실습](../01-backup-restore/README.md)을 마친 작업 디렉터리에서 실행했습니다.

```bash
python scripts/tuning.py \
  --workspace "$LAB_WORKSPACE" \
  --pg-bin /usr/lib/postgresql/18/bin \
  --data-mode unmodified --clients 2 --transactions 100 --rounds 4

python scripts/tuning.py \
  --workspace "$LAB_WORKSPACE" \
  --pg-bin /usr/lib/postgresql/18/bin \
  --data-mode masked --clients 2 --transactions 100 --rounds 4
```

첫 번째는 원본 값을 유지한 비공개 복원본, 두 번째는 식별값을 치환한 복제본에서 실행했습니다. 두 모드의 DB와 결과 파일은 분리했습니다.

[측정 스크립트](../../scripts/tuning.py)에서 파일 ID 1개·10개·100개를 조회하는 세 조건을 구성했습니다. 원래 SQL의 전체 열 조회, 삭제 상태 조건, 현재 수집 묶음 제외 조건과 정렬을 유지했습니다. 과거 이력이 많은 파일을 선택했으며, 실제 서비스의 요청 비중을 재현한 구성은 아닙니다.

각 조건을 세 번 예열한 뒤 `pgbench`로 클라이언트 2개가 각각 100회씩 실행하도록 했습니다. 인덱스가 있는 경우와 없는 경우를 4라운드씩 측정하고, 라운드마다 실행 순서를 바꿨습니다. 다른 인덱스는 유지했고 인덱스 사용을 강제하는 설정은 넣지 않았습니다.

실습 DB의 `pg_stat_statements`에서 대상 SQL의 실행 횟수와 평균 실행 시간, 편차, 버퍼 접근을 수집했습니다. 조건별 200회 실행 여부와 조회 결과의 값·중복 개수가 같은지도 확인했습니다. `EXPLAIN (ANALYZE, BUFFERS, FORMAT JSON)`으로 실제 스캔 방식과 버퍼 사용량을 함께 비교했습니다.

## 결과

원본 복원본의 수집 이력 2,692행과 수집 묶음 27행을 대상으로 총 4,800회 측정했습니다. 업체 1개가 이전 이력 비교 조건을 충족했습니다. 인덱스 유무에 따른 조회 결과는 같았습니다.

| 조회하는 파일 ID 수 | 반환 행 수 | 인덱스 없음 | 인덱스 있음 | 없음 ÷ 있음 |
| --- | ---: | ---: | ---: | ---: |
| 1개 | 5 | 0.6173ms | 0.1044ms | 5.91배 |
| 10개 | 41 | 1.1705ms | 0.4749ms | 2.46배 |
| 100개 | 247 | 2.9587ms | 2.3921ms | 1.24배 |

시간은 각 조건에서 얻은 4개 라운드의 평균 실행 시간에 대한 중앙값입니다. 파일 ID 1개 조회에서는 `Seq Scan`이 해당 복합 인덱스의 `Index Scan`으로 바뀌었고, 대표 실행계획의 전체 shared buffer hit가 306회에서 9회로 줄었습니다. 물리 디스크 read는 두 조건 모두 0이었습니다.

100개를 조회할 때는 효과가 1.24배로 작아졌습니다. 두 조건 모두 `Sort`가 남아 있어 이 인덱스가 정렬 작업까지 없애지는 못했습니다. 파일 ID 1개 조회의 절대 시간 차이는 약 0.513ms였습니다.

마스킹 복제본에서도 별도로 4,800회 측정했습니다. 파일 ID 1개 조회는 0.5927ms에서 0.1164ms로 줄었습니다. 원본 복원본과 섞지 않고 별도 결과로 남겼습니다.

결과 파일: [원본 복원본 측정·실행계획](../../results/tuning.json), [마스킹 복제본 측정](../../results/tuning-masked.json)

## 막혔던 점

처음 마스킹 복제본을 만드는 과정에서 `42P06` 오류가 발생했습니다. 실제 백업에 이미 `masked` 스키마가 있어서 실습용 스키마 이름과 충돌했습니다. 실습용 이름을 `pgops_masked`로 바꾸고, 기존 `masked` 스키마가 있는 경우를 코드 검증에 추가했습니다.

운영 SQL의 지연 순위를 기준으로 대상을 고르는 데에도 한계가 있었습니다. 확인 당시 운영 DB에는 `pg_stat_statements`가 설치되어 있지 않았고, 조회한 인덱스 사용 통계도 모두 0이었습니다. 따라서 운영에서 가장 느리거나 가장 많이 쓰는 SQL이라는 근거는 확보하지 못했습니다. 이번 선정 근거와 결과는 실제 조회 조건에 맞는 기존 인덱스의 효과 확인으로 한정했습니다.

## 배운 점

같은 인덱스도 조회 범위가 넓어지면 효과가 달라졌습니다. 실행 시간과 함께 실행계획, 반환 행 수, 버퍼 접근을 확인하니 어느 조건에서 이점이 큰지 설명할 수 있었습니다. 5.91배라는 비율도 실제 시간 차이인 0.513ms와 함께 해석해야 했습니다.

이번 실험으로 복원본에서 기존 인덱스의 효과를 확인했습니다. 운영의 느린 SQL을 발견해 새 인덱스를 배포한 경험으로 확대할 수는 없습니다. 운영 개선으로 연결하려면 실제 호출 빈도와 지연 시간을 수집하고, 인덱스의 쓰기 비용도 함께 측정해야 합니다.

반복 측정에서는 캐시가 채워진 상태를 사용했습니다. 복원 과정에서 데이터 배치와 통계가 다시 만들어지고, 마스킹 과정에서는 행 크기와 압축률도 달라질 수 있습니다. 같은 빈도의 파일 중 선택되는 값도 달라질 수 있어 두 모드의 시간 차이를 마스킹만의 영향으로 해석하지 않았습니다. 원본 값과 SQL 매개변수는 비공개로 보관하고, 공개 실행계획에서는 조건식·상수·정렬 키를 제거했습니다.
