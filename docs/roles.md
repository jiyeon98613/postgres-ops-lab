# 로그인 계정별 권한 검증

복제한 조회 DB에서 서로 다른 비밀번호를 가진 계정으로 실제 접속합니다. 단순히 슈퍼유저 세션에서 `SET ROLE`만 바꿔 결과를 확인하는 방식보다 인증과 권한을 함께 점검할 수 있습니다.

| 역할 | 허용 | 거부 |
| --- | --- | --- |
| 읽기 전용 | 이력 조회, 향후 생성되는 테스트 테이블 조회 | INSERT·UPDATE·DELETE·DROP |
| 애플리케이션 | 이력 조회, 테스트 테이블 INSERT·UPDATE | DELETE·DDL·DROP·소유자 역할 전환 |
| 스키마 소유자 | 소유한 테스트 스키마의 DDL·DELETE | 역할 생성 |

계정은 슈퍼유저·DB 생성·역할 생성·복제 권한을 갖지 않습니다. 스키마 소유자는 클러스터 슈퍼유저와 다릅니다. 운영 관리 권한을 제한하는 예시로 범위를 정합니다.

테스트용 테이블의 쓰기는 매 검사 후 rollback합니다. 원래 복원한 운영 데이터에는 시험용 INSERT·DELETE를 수행하지 않습니다. `ALTER DEFAULT PRIVILEGES`를 설정한 뒤 만든 테이블에도 읽기 권한이 적용되는지 검사하고, 잘못된 비밀번호로 로그인할 수 없는지도 확인합니다.

```bash
python scripts/roles.py \
  --workspace "$LAB_WORKSPACE" \
  --pg-bin /usr/lib/postgresql/18/bin
```

거부 검사는 권한 부족 SQLSTATE `42501`을 확인합니다. 다른 오류를 권한 차단 성공으로 세지 않습니다. 로그인 거부는 libpq가 SQLSTATE를 제공하지 않을 수 있어 비밀번호 인증 실패 여부를 별도로 확인합니다.

이 설계는 격리된 실습 DB에 적용됩니다. 운영 애플리케이션이 실제로 요구하는 DELETE 권한, 환자별·업체별 접근 범위, 제한 함수 계약은 운영 코드를 확인해 별도로 판단해야 합니다. 실습 성공을 운영 계정 분리나 민감정보 접근 통제의 구축 완료로 기재하지 않습니다.
