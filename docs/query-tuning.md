# 실제 수집 이력 SQL의 기존 인덱스 비교

## 대상과 선정 근거

문서 수집 중 이번에 발견한 Drive 파일 ID의 이전 처리 이력을 찾는 조회를 대상으로 합니다. 애플리케이션의 `document_discovery._previous_items()`는 업체와 파일 ID로 `staging.change_items`를 좁힌 뒤 `staging.change_sets`와 연결하고 최신 생성 시각 순으로 가져옵니다.

기존 migration `a8d4f2c61b90`에는 다음 인덱스가 정의되어 있습니다.

```sql
CREATE INDEX ix_change_items_vendor_business_created
ON staging.change_items (vendor_id, business_key, created_at);
```

업체와 파일 ID를 조건으로 사용하므로 비교할 가치가 있는 후보입니다. 이 사실만으로 운영에서 가장 유용한 인덱스이거나 실제로 느린 SQL이라고 판단하지 않습니다. 배포된 코드, 실제 백업의 인덱스 존재, 이력 데이터 양을 확인한 후 측정합니다. 인덱스가 없거나 비교할 이전 이력이 없으면 해당 실습은 중단합니다.

## 데이터와 SQL

복구가 검증된 DB에서 두 이력 테이블의 행 수·열 구조·인덱스를 유지한 복제본을 만듭니다. UUID와 파일 ID는 같은 값이 같은 대체값을 갖도록 치환하고, 모든 시각에는 같은 차이를 적용합니다. 이력 결합 개수와 조회 키의 고유값 개수가 유지되는지 확인합니다.

JSON의 키·문자열·숫자 값은 바꿉니다. 원문을 그대로 공개하거나 비식별화가 완전하다고 주장하지 않습니다. 치환 후에도 데이터 파일을 Git에 올리지 않습니다.

측정 SQL은 애플리케이션처럼 두 테이블의 전체 열을 조회합니다. `COUNT(*)`나 일부 ID만 조회하는 SQL로 바꾸지 않습니다. 삭제 상태 조건, 현재 수집 묶음 제외, 정렬 조건도 유지합니다. [SQL 예시](../sql/discovery-history.sql)의 파일 ID 개수는 예시이며, 실제 측정에서는 선택된 개수만큼 IN 목록을 구성합니다.

## 비교 방법

1. 이전 이력이 있는 업체 최대 3개를 대상으로, 이력 빈도가 높은 키 1개·최대 10개·최대 100개 조회를 구성합니다. 이것은 실시간 요청 비중을 재현한 트래픽은 아닙니다.
2. 기존 인덱스를 유지한 상태와 해당 인덱스 하나만 제거한 상태를 비교합니다. 다른 인덱스는 유지하고 planner 옵션으로 인덱스 사용을 강제하지 않습니다.
3. 매 조건에서 동일 SQL을 3번 예열합니다. 격리된 실습 DB의 `pg_stat_statements`를 초기화한 뒤 `pgbench`로 실행합니다.
4. 기본값은 클라이언트 2개, 클라이언트당 100회, 4라운드입니다. 라운드마다 두 조건의 실행 순서를 바꿉니다.
5. SQL의 실제 실행 횟수가 기대한 횟수와 같은지 확인합니다. 두 조건의 결과 행 값과 중복 개수도 비교합니다.
6. `EXPLAIN (ANALYZE, BUFFERS, FORMAT JSON)`에서 스캔 방식, 실제 행 수, 실행 시간, 버퍼 접근을 확인합니다. 공개 결과에서는 식별값이 포함될 수 있는 조건식·상수·정렬 키를 제외합니다.

```bash
python scripts/tuning.py \
  --workspace "$LAB_WORKSPACE" \
  --pg-bin /usr/lib/postgresql/18/bin \
  --clients 2 --transactions 100 --rounds 4
```

## 결과 해석

`pg_stat_statements`는 직접 만든 코드가 아니라 PostgreSQL의 SQL 실행 통계 확장입니다. 이 실습에서는 실행 횟수, 평균·최소·최대 실행 시간, 표준편차, 버퍼 hit/read를 수집합니다. `pgbench`는 정한 SQL을 반복 실행하는 부하 도구입니다.

라운드별 평균 실행 시간의 중앙값을 각 조건에서 비교합니다. 지연 시간이 매우 작거나 편차가 큰 경우 비율만 강조하지 않습니다. 인덱스를 사용하지 않거나 차이가 없다면 그 결과를 그대로 남깁니다.

이 검증은 **기존 인덱스의 효과를 복제 환경에서 확인하는 실험**입니다. 운영 느린 쿼리 목록에서 발견해 새 인덱스를 추가한 성능 개선 사례와 구분합니다.

## 한계

- 치환된 JSON과 문자열 때문에 행 크기·압축률·물리적 배치가 달라질 수 있습니다.
- 다른 테이블을 참조하는 외래키와 RLS 정책은 성능용 두 테이블 복제에 포함하지 않습니다.
- OS 캐시를 비우지 않은 반복 조회이며, 운영 서버 부하·네트워크 지연·실제 요청 비중을 재현하지 않습니다.
- 인덱스의 쓰기 비용과 장기적인 디스크 사용 변화는 별도로 측정해야 합니다.
- 운영 데이터의 분포가 작다면 개선 폭이 작을 수 있습니다. 임의로 데이터를 늘린 결과를 운영 규모의 성과로 표시하지 않습니다.
