# 실제 수집 이력 SQL의 기존 인덱스 비교

## 대상과 선정 근거

문서 수집 중 이번에 발견한 Drive 파일 ID의 이전 처리 이력을 찾는 조회를 대상으로 합니다. 애플리케이션의 `document_discovery._previous_items()`는 업체와 파일 ID로 `staging.change_items`를 좁힌 뒤 `staging.change_sets`와 연결하고 최신 생성 시각 순으로 가져옵니다.

기존 migration `a8d4f2c61b90`에는 다음 인덱스가 정의되어 있습니다.

```sql
CREATE INDEX ix_change_items_vendor_business_created
ON staging.change_items (vendor_id, business_key, created_at);
```

업체와 파일 ID를 조건으로 사용하므로 비교할 가치가 있는 후보입니다. 이 사실만으로 운영에서 가장 유용한 인덱스이거나 실제로 느린 SQL이라고 판단하지 않습니다. 배포된 코드, 실제 백업의 인덱스 존재, 이력 데이터 양을 확인한 후 측정합니다. 인덱스가 없거나 비교할 이전 이력이 없으면 해당 실습은 중단합니다.

## 데이터와 SQL

주 측정은 실제 백업을 새 DB에 전체 복원해 원본 값을 유지한 상태에서 수행합니다. 이 DB와 SQL 인자는 보호된 서버 밖으로 내보내지 않습니다. 비식별 복제본에서도 비교 절차를 검증하기 위해, 별도로 두 이력 테이블의 행 수·열 구조·인덱스를 유지한 복제본을 만듭니다. UUID와 파일 ID는 같은 값이 같은 대체값을 갖도록 치환하고, 모든 시각에는 같은 차이를 적용합니다. 이력 결합 개수와 조회 키의 고유값 개수가 유지되는지 확인합니다.

JSON의 키·문자열·숫자 값은 바꿉니다. 원문을 그대로 공개하거나 비식별화가 완전하다고 주장하지 않습니다. 치환 후에도 데이터 파일을 Git에 올리지 않습니다.

측정 SQL은 애플리케이션처럼 두 테이블의 전체 열을 조회합니다. `COUNT(*)`나 일부 ID만 조회하는 SQL로 바꾸지 않습니다. 삭제 상태 조건, 현재 수집 묶음 제외, 정렬 조건도 유지합니다. [SQL 예시](../sql/discovery-history.sql)의 파일 ID 개수는 예시이며, 실제 측정에서는 선택된 개수만큼 IN 목록을 구성합니다.

## 비교 방법

1. 이전 이력이 있는 업체 최대 3개를 대상으로, 이력 빈도가 높은 키 1개·최대 10개·최대 100개 조회를 구성합니다. 이것은 실시간 요청 비중을 재현한 트래픽은 아닙니다.
2. 기존 인덱스를 유지한 상태와 해당 인덱스 하나만 제거한 상태를 비교합니다. 다른 인덱스는 유지하고 planner 옵션으로 인덱스 사용을 강제하지 않습니다.
3. 매 조건에서 동일 SQL을 3번 예열합니다. 격리된 실습 DB의 `pg_stat_statements`를 초기화한 뒤 `pgbench`로 실행합니다.
4. 기본값은 클라이언트 2개, 클라이언트당 100회, 4라운드입니다. 라운드마다 두 조건의 실행 순서를 바꿉니다.
5. SQL의 실제 실행 횟수가 기대한 횟수와 같은지 확인합니다. 두 조건의 결과 행 값과 중복 개수도 비교합니다.
6. `EXPLAIN (ANALYZE, BUFFERS, FORMAT JSON)`에서 스캔 방식, 실제 행 수, 실행 시간, 버퍼 접근을 확인합니다. 공개 결과에서는 식별값이 포함될 수 있는 조건식·상수·정렬 키를 제외합니다.

```bash
python scripts/tuning.py \
  --workspace "$LAB_WORKSPACE" \
  --pg-bin /usr/lib/postgresql/18/bin \
  --data-mode unmodified --clients 2 --transactions 100 --rounds 4
```

`--data-mode masked`가 기본값이며 식별값을 치환한 별도 비교를 수행합니다. 두 모드는 서로 다른 DB와 결과 파일을 사용합니다.

## 결과 해석

2026-10-17 정기 백업의 원본 값을 유지한 복원본에서 이력 2,692행·수집 묶음 27행으로 총 4,800회 실행했습니다. 업체 1개의 이전 이력이 비교 조건을 충족했습니다. 조회 결과는 두 조건에서 동일했습니다.

| 조회하는 파일 ID 수 | 반환 행 수 | 인덱스 없음 | 인덱스 있음 | 실행 시간 비율 |
| --- | ---: | ---: | ---: | ---: |
| 1개 | 5 | 0.6173ms | 0.1044ms | 5.91배 |
| 10개 | 41 | 1.1705ms | 0.4749ms | 2.46배 |
| 100개 | 247 | 2.9587ms | 2.3921ms | 1.24배 |

수치는 각 조건의 4라운드 평균 실행 시간에 대한 중앙값입니다. 1개 조회에서 실행계획은 전체 이력 테이블 스캔에서 해당 복합 인덱스 스캔으로 바뀌었습니다. 대표 실행계획의 shared buffer hit는 전체 쿼리 기준 306회에서 9회로 줄었습니다. 물리 디스크 read는 양쪽 모두 0이므로 이를 디스크 읽기 감소율로 표현하지 않습니다.

100개 조회는 인덱스로 접근하는 행·블록이 늘어나 효과가 작아졌습니다. 두 조건 모두 별도의 Sort가 남아 있어 이 인덱스가 정렬을 제거했다고 볼 수 없습니다. 1개 조회의 절대 차이는 약 0.513ms로, 배수와 함께 실제 지연 차이를 보아야 합니다. [반복 측정과 대표 실행계획](../results/tuning.json)

운영 인덱스 사용 통계는 조회 시 모두 0이고 운영 `pg_stat_statements`도 설치되지 않았습니다. 선정 근거는 조회 조건과 기존 인덱스의 일치이며, 운영 통계에 따른 빈도·지연 순위는 확정할 수 없습니다. 배포된 조회 함수와 로컬 기준 함수의 AST 해시 일치를 확인했으며, 근거는 [소스 확인 결과](../results/source-context.json)에 있습니다.

`pg_stat_statements`는 PostgreSQL의 SQL 실행 통계 확장입니다. 이 실습에서는 실행 횟수, 평균·최소·최대 실행 시간, 표준편차, 버퍼 hit/read를 수집합니다. `pgbench`는 정한 SQL을 반복 실행하는 부하 도구입니다.

라운드별 평균 실행 시간의 중앙값을 각 조건에서 비교합니다. 지연 시간이 매우 작거나 편차가 큰 경우 비율만 강조하지 않습니다. 인덱스를 사용하지 않거나 차이가 없다면 그 결과를 그대로 남깁니다.

이 검증은 **기존 인덱스의 효과를 복제 환경에서 확인하는 실험**입니다. 운영 느린 쿼리 목록에서 발견해 새 인덱스를 추가한 성능 개선 사례와 구분합니다.

마스킹 복제본도 별도로 4,800회 실행했습니다. 파일 1개 조회는 0.5927ms → 0.1164ms로 같은 방향의 효과를 보였습니다. 원본 복원본 수치와 섞지 않고 [별도 집계](../results/tuning-masked.json)로 보관합니다.

## 한계

- 원본 복원본도 복원 과정에서 물리적 배치와 통계가 다시 만들어집니다. 마스킹 비교에서는 JSON과 문자열 치환에 따라 행 크기·압축률도 달라질 수 있습니다.
- 다른 테이블을 참조하는 외래키와 RLS 정책은 마스킹용 두 테이블 복제에 포함하지 않습니다. 원본 값 비교는 전체 스키마를 복원한 DB에서 수행합니다.
- OS 캐시를 비우지 않은 반복 조회이며, 운영 서버 부하·네트워크 지연·실제 요청 비중을 재현하지 않습니다.
- 인덱스의 쓰기 비용과 장기적인 디스크 사용 변화는 별도로 측정해야 합니다.
- 키 빈도가 같을 때 치환 값의 정렬 순서에 따라 두 모드에서 선택한 파일이 달라질 수 있습니다. 모드 간 지연 차이를 마스킹만의 효과로 해석하지 않습니다.
- 운영 데이터의 분포가 작다면 개선 폭이 작을 수 있습니다. 임의로 데이터를 늘린 결과를 운영 규모의 성과로 표시하지 않습니다.

참고: [pg_stat_statements](https://www.postgresql.org/docs/18/pgstatstatements.html), [EXPLAIN](https://www.postgresql.org/docs/18/sql-explain.html), [pgbench](https://www.postgresql.org/docs/18/pgbench.html)

## 실행 중 수정한 점

실제 백업에 이미 `masked` 스키마가 있어 최초 마스킹 단계가 `42P06` 이름 충돌로 중단됐습니다. 실습용 `pgops_masked` 스키마를 사용하도록 수정하고, 기존 `masked` 스키마가 있는 경우를 코드 검증에 추가했습니다. 기존 스키마를 삭제하거나 재사용하지 않았습니다.
